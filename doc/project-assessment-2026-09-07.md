# ZahnerFlow 项目全局评估报告

评估开始：2026-09-07；整理完成：2026-09-08。应用版本：1.0.11。代码基线：`0d4c8d3`，开始评估时工作区无未提交修改。

本报告建立后续讨论的共同基线，区分代码事实、适用性判断和待验证事项。本次新增文档，不改变功能、界面、依赖、设备行为或现行架构。建议编号 R01—R07 可作为后续任务的引用标识。

## 1. 总体判断

**ZahnerFlow 的定位是面向特定实验设备组合的本地科研实验工作台。核心价值是把“设定条件—执行测量—重复流程—记录结果”连接成一条可追溯的实验链。**

现有架构与这一定位基本匹配：单进程协调降低部署复杂度，统一执行计划减少预览与执行差异，SQLite 适合保存本地实验记录，桌面壳提供文件路径和进程管理能力。源码同时呈现出较鲜明的深色玻璃态设计，以及逐步集中业务规则的代码组织方式。

目前更适合描述为“具备完整业务骨架、可继续工程化的专用科研软件”。构建和基础接口可运行已有本次证据；长时真机可靠性、所有交互状态的易用性与跨平台交付质量尚不能据此判定。

| 维度 | 判断 | 证据边界 |
| --- | --- | --- |
| 产品目的 | 清晰，围绕电化学与环境条件协同实验 | 根据节点、驱动、执行和报告代码判断 |
| 架构适配 | 适合本地单工作站、串行实验 | 核对运行时与路由，并完成隔离启动检查 |
| 界面风格 | 深色、玻璃态、科技感、三栏工作台 | 根据当前组件和样式判断，未进行屏幕视觉验收 |
| 代码组织 | 有明确领域边界，但类型与模块粒度仍不均衡 | 源码审阅、类型构建与 lint |
| 工程保障 | 有版本与构建基础，验证及交付入口尚需整理 | 本次命令结果与当前 CI、脚本核对 |
| 应用成熟度 | 适合继续面向实际实验场景打磨 | 未做真机实验、长时运行和安装包验收 |

## 2. 项目究竟解决什么问题

目标用户是需要重复执行多条件电化学实验的研究人员或实验操作者。典型任务是设置温度与气氛，等待条件变化，执行电化学测量，再按循环或阶梯参数重复，最后追溯某一次测量的流程、条件、结果与异常。

产品价值集中在三处：

1. **减少重复操作。** 节点、循环、工作流块和高级测量把操作步骤组合为可重复流程。
2. **保持执行解释一致。** 后端计划统一提供展开步骤、自动测量边界、起点与 ETA，界面消费后端事实。
3. **保留实验上下文。** 执行记录与工作流快照、节点结果、环境信息和输出文件关联，便于回查。

当前能力来自实际代码：[节点配置](../apps/frontend/src/types/NodeConfiguration.ts)、[执行语义](../apps/python_backend/runtime/execution_semantics.py)、[执行记录器](../apps/python_backend/runtime/execution_recorder.py)、[实验记录界面](../apps/frontend/src/components/report/ReportGeneratorModal.tsx)。

| 能力组 | 当前实现 | 限定 |
| --- | --- | --- |
| 电化学测量 | 恒电位/恒电流 EIS、OCP、计时电流/电位、电压/电流斜坡，以及展开为基础步骤的切换和阶梯节点 | 真机接入由 Zahner/Thales 驱动实现 |
| 环境控制 | AI-518P 炉温程序及点变温、MFC 扫描与流量设定 | 支持当前驱动协议，不应概括为支持任意炉子或 MFC |
| 编排 | 等待、定时、循环、工作流块、展开预览和从合法展开步骤开始 | 不等于任意条件分支、并行任务调度或断电续跑 |
| 观察与追溯 | IVT/EIS 图表、设备快照、执行记录、相似地图和报告 | 本次未验证全部结果文件和报告分页 |
| 模拟 | 炉子、MFC、Zahner 均有模拟设备类 | 适合流程演练，不能替代物理设备精度与异常行为验证 |

包元数据中的 `gamry` 关键词不足以证明设备支持；当前设备目录和工作站契约确认的是 Zahner、Furnace 和 MFC。

## 3. 架构与数据流

浏览器开发模式为 Vite 前端与 Python 后端；桌面模式为 Electron 承载 React 页面，并启动同一套 Python 后端。后端主进程承载 FastAPI、Socket.IO、执行与设备协调，阻塞调用使用线程；“单进程”不表示“没有并发”。

| 层次 | 主要入口 | 职责 |
| --- | --- | --- |
| 展示与编辑 | `App.tsx`、组件、Zustand stores | 编辑流程、展示后端快照、管理视图状态 |
| 通信 | `runtimeClient.ts` | REST 请求、错误映射与 Socket.IO 连接 |
| 运行协调 | `runtime/app_runtime.py` | 连接状态、轮询、执行协调、状态持久化和广播 |
| 规划与执行 | `execution_planner.py`、`execution_engine.py` | 展开、校验、估时、执行状态与步骤调用 |
| 设备 | `device_manager.py`、`devices/*` | 驱动调用、串口/主机连接及设备专属行为 |
| 记录 | `database.py`、`execution_recorder.py` | SQLite 业务记录和结果文件索引 |
| 桌面壳 | `apps/desktop/src/main.ts` | 窗口、路径、IPC、后端进程和健康检查 |

主链路：画布节点 → `runtimeClient` → 执行路由 → 后端计划 → 执行引擎 → 设备驱动 → 执行记录/状态广播 → 图表与报告。

值得保留的设计是：运行状态以后端为准；共享契约从 Python 生成；预览与执行共用规划入口；设备重连用代次排除旧结果；曲线按执行、节点和循环隔离；终态保留结果直到显式重置。这些规则直接服务于实验可追溯性。

当前边界也清楚：同一时间只允许一条活跃执行；物理连接不会在进程重启后被当作仍然存在；遗留活跃执行在启动时标记失败。用户档案用于记录归属和设置，当前路由没有形成身份认证与权限控制体系。SQLite 初始化包含建表和补列逻辑，不应把应用版本号理解为数据库迁移版本。

## 4. 当前设计风格及适用性

### 4.1 视觉语言

当前源码呈现的是**深色玻璃态科研工作台**：

- 基底为深蓝黑 `#0f172a`，面板使用半透明背景、模糊、细亮边与阴影。
- 蓝色作为主要操作色，绿、橙、红承担成功、警告、错误语义；设备、节点和循环层级有专用颜色。
- 英文与数字主要使用 Oxanium，中文使用 Noto Sans SC Variable，并设置独立字距。
- 主视图由顶栏、左侧节点库、中间画布、右侧属性栏、底部状态栏组成，设备和记录等功能通过浮层展开。
- Canvas 粒子与波形背景提供动态效果；组件有悬浮、按压、进度环等反馈。

依据：[基础令牌](../apps/frontend/src/styles/_base.scss)、[布局](../apps/frontend/src/styles/_layout.scss)、[背景组件](../apps/frontend/src/components/ParticleBackground.tsx)、[应用根组件](../apps/frontend/src/App.tsx)。这是对当前实现的归纳，不是对未来界面必须沿用此风格的要求。

### 4.2 与实验工作的匹配程度

三栏结构适合“选节点—排流程—改参数”的桌面操作，彩色节点和循环有助于分组。语义令牌、统一浮层、滚动区性能处理、全局焦点样式与 CSS 减少动画规则，说明界面已有一致性和可操作性的基础。

需要后续验证的是长时间读数与复杂流程操作：透明背景上的次级文字对比度、不同缩放下的数值和单位辨识、多个浮层之间的任务切换，以及背景动画与曲线同屏时的资源消耗。不能仅凭模糊效果存在，就认定性能差；同样不能凭已有性能代码就认定所有设备上均流畅。

Electron 最小窗口为 `1180 × 760`，CSS 有窄屏规则，但产品仍明显以桌面操作为中心。移动端、触屏和键盘完整操作能力需要单独验证。

一个具体的交互边界是：工具栏停止操作采用长按 1 秒，EIS 在执行注册表中为不可中断步骤。因而“发出取消请求”和“物理测量停止”可能存在时间差。文案及反馈应能准确说明当前状态；这也是后续 R01 的重点。

## 5. 代码风格与维护性

### 5.1 已形成的风格

| 范围 | 当前代码风格 | 优势与限制 |
| --- | --- | --- |
| 前端逻辑 | 函数组件、Hooks、Zustand；camelCase 与 PascalCase；选择器和配置表描述业务语义 | 有利于集中状态解释，但部分组件仍承担较多职责 |
| 前端类型 | Python 契约生成共享 TypeScript，通信边界使用泛型与 `unknown` | 契约源头明确；前端 `strict`、未使用项检查未全面启用 |
| 样式 | SCSS 按领域拆分，CSS `@layer` 和语义令牌；BEM 类名为主 | 有统一基础；仍有内联样式、工具类和旧式导入混合 |
| 后端 | snake_case、协调类、函数模块、dataclass 和 Pydantic | 领域意图清楚；大量 `dict` 及路由内 SQL 使部分约束留在运行时 |
| 文档与注释 | 中文业务说明与英文代码标识/技术注释混用 | 贴近中文团队；历史说明应持续与代码同步 |

本次搜索 `apps/frontend/src` 未发现 `console.log/debug/info` 调试输出或 `index.ts` barrel 文件；普通 HTTP 请求与 Socket.IO 建连的匹配均集中在 `runtimeClient.ts`。这些结果支持通信和导入规则正在实际执行，但不代表所有业务判断都已消除重复。

### 5.2 主要维护成本

按已跟踪的 `.py/.ts/.tsx/.cts/.scss/.css` 文件统计，共 184 个文件、约 4.06 万非空行。这个口径包含共享生成文件，只用于判断规模。

几个维护热点超过千行非空代码或样式：`app_runtime.py` 约 1344 行、`UserSettingsModal.tsx` 约 1051 行、`ReportGeneratorModal.tsx` 约 1040 行、`_chart-modal.scss` 约 1476 行。文件长本身不构成缺陷，但跨设备协调、状态副作用、编辑表单、报告加载等责任集中，修改时理解成本较高。

类型构建成功不等于严格类型完备：[前端 tsconfig](../apps/frontend/tsconfig.json) 中 `strict: false`、`noUnusedLocals: false`、`noUnusedParameters: false`。后端路由使用字典请求和直接 SQL，后续新增字段时仍需明确校验、事务与错误边界。

另有一个容易误导维护者的残留：[TypeScript 展开器](../apps/shared/loopUnroller.ts) 仍描述旧式 0 起始循环路径；本次在 `apps`、`packages` 的 TS/TSX 中未找到外部调用。当前真实执行使用 Python Planner。应先确认依赖再处理残留，不能把它误认为另一套当前执行事实。

## 6. 适用范围

| 场景 | 适用性判断 | 原因或前提 |
| --- | --- | --- |
| 单台实验电脑控制现有 Zahner、炉子、MFC 组合 | 架构匹配，需设备验收 | 本地运行、直接驱动、串行执行、明确记录归属 |
| 多温度、多气氛、重复电化学测量 | 业务匹配 | 已有相关节点、循环、环境上下文和记录链路 |
| 模拟流程演示与操作训练 | 有实现基础 | 三类模拟器具备；本次未执行完整模拟测量 |
| 实验结果回查和内部报告 | 有实现基础 | 工作流快照、执行记录、结果索引、HTML/PDF 导出 |
| 投稿图或可编辑科学排版 | 需补充导出能力 | 当前 PDF 导出将 HTML 渲染为 Canvas 后嵌入 PDF，不等于矢量或可编辑科研图 |
| 不同操作者轮流使用同一电脑 | 有条件适用 | 有用户档案和设置；实验仍是单执行，用户档案不提供权限隔离 |
| 多人远程协作、多个工作站并行调度 | 超出现行设计 | 缺少对应鉴权、资源调度与多运行时模型 |
| 手机控制或完整跨平台真机运行 | 未建立验证结论 | 有响应式和平台打包配置，但协议、路径、安装与交互需逐平台实测 |
| 断电续跑、确定时限急停、无人值守保障 | 当前代码和本次证据不足以承诺 | 无跨进程续跑，取消取决于步骤可中断性，未做硬件故障与长期运行验收 |

网络范围也应按现有实现理解：Python 默认绑定回环地址，而 Vite 开发服务器配置 `host: true` 并代理设备 API；本地运行设计不等于所有开发端口都只接受本机访问。当前没有远程部署验收结论。

## 7. 后续修改建议

以下优先级按“继续作为本地科研工作台打磨”的目标提出，尚未实施。

| 编号 | 优先级 | 已知事实与修改方向 | 可验收结果 |
| --- | --- | --- | --- |
| R01 | 高 | 复核停止、暂停、错误和设备失联的操作语义；长按停止与 EIS 不可即时中断需要清晰反馈 | 按节点列出暂停/取消响应边界；操作入口、等待状态和真实设备状态可解释且一致 |
| R02 | 高 | 整理启动、测试、构建和发布入口；部分脚本指向缺失文件，CI 当前只检查版本/发布范围 | 保留的脚本有真实目标；建立符合“不提交测试源码”规则的外部或忽略目录验证方式；所有构建/发布入口有版本前置检查 |
| R03 | 高 | 明确依赖重现与数据恢复方式；`pnpm-lock.yaml` 被忽略，`uv.lock` 已跟踪；数据库有补列逻辑 | 新环境安装可复现；数据库与测量文件的备份/恢复范围明确；后续结构变化有迁移与恢复证据 |
| R04 | 中 | 按真实职责逐步拆分大型组件和协调器内部逻辑，局部加强类型和输入校验 | 保持单一 `AppRuntime` 与通信入口；被修改边界具备明确类型/校验；消除相关 lint 警告 |
| R05 | 中 | 围绕读数、流程识别和运行反馈评估现有视觉设计，再决定局部调整或重新设计 | 给定分辨率、系统缩放、键盘路径、复杂流程和长时图表的操作结果；有对比度和性能证据 |
| R06 | 中 | 明确内部报告与科研数据/图形导出需求 | 原始文件可追溯；按实际需求确定结构化数据、矢量图或排版报告；验证单位、精度和分页 |
| R07 | 低 | 核对未调用展开器、旧脚本、元数据和设计复核日期，清理造成错误理解的历史残留 | 文档、目录和真实运行入口一致；删除或保留均有调用证据 |

R02 的具体证据：根 `setup` 指向缺失的 `scripts/setup.js`，部分 `test:*` 指向不存在的 `test/`，前端 `serve` 指向缺失的 `server.py`；根 `build` 和 `desktop:build` 有版本前置检查，但 `desktop:dist`、`desktop:dist:win/mac` 及部分子包构建入口没有同样的内置检查。

R05 应以实际实验任务为评价基准：当前风格有辨识度，但保留或改变哪些视觉元素应由后续需求决定。本报告没有创建新的视觉方案，也没有将旧设计设为后续任务默认模板。
