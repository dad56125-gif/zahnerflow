## 固定流程

1. 开始发布时固定上一次已验收电脑版的版本、源码 SHA 和安装包哈希，不能使用移动的 HEAD 作为基线。
2. 固定新发布源码 SHA，检查前者是后者的祖先。按 Git 父子关系提取范围，未合并分支单独说明；simu 保持独立。
3. 复核实际差异，填写阶段清单。每个提交只能属于一个阶段，但阶段可以包含多种变化：UI、Bug、功能、数据结构／契约、文档、合并、工程维护。类型不是提交数量或功能数量；不能只按标题认定修复。
4. 数据影响必须另写：SQL 表／列／迁移、共享契约、已有 JSON 字段扩展、会话状态或无结构变化。共享契约变化不自动意味着 SQL 迁移。
5. 生成流程图与逐提交清单，检查提交无遗漏／无重复、分支分出及合并父提交、版本、已验证和未验证边界。总览是阶段演进图；逐提交父 SHA 才是精确祖先关系。
6. 安装包验收后保存本轮清单与图，登记新发布基线（源码 SHA、版本、安装包 SHA256、验证证据）。下一轮从该基线开始；不能覆盖旧轮次。2.12.0 的基线为 9751988。
