# Zennium 直连驱动：两条路径的并行研究

日期：2026-09-19。目标：评估 ZahnerFlow 能否省去 Term，由自身进程驱动工作站。两个子代理分别分析厂商 HAL 与直接 D2XX 路径，主代理核查共同的主机服务依赖并复核关键反汇编证据。

本次只分析安装包、文档、PE 结构和反汇编，没有加载执行厂商 DLL、枚举实际 USB 设备、打开仪器或下发命令。所有结论均针对安装包中的具体二进制，不代表已完成真机直连。

## 结论

两条路径均有研究入口，但都没有达到可以读取仪器电位或执行 EIS 的闭环。使用少量测量功能可以缩小测量接口范围，却不能自动省略工作站依赖的主机通信服务。

**复用 HAL 更适合用作协议研究参照；直接 D2XX 更符合当前 64 位单进程后端的集成目标，但前提是实际仪器确实使用 FTDI 接口，且其上层协议得到验证。** 这是基于当前证据的路线判断，不是已经验证的替代驱动。

## 2. 路径一：直接复用厂商 HAL

目标结构：`ZahnerFlow -> 本地调用适配 -> FTDIHAL -> FTD2XX -> USB`。

### 已确认的限制

1. **位数不匹配。** 包内 HAL 是 x86，不能由当前 64 位 Python 进程直接加载。增加普通 ctypes 包装或一个 x64 转接 DLL 都不能消除这个限制。
2. **导出函数不是普通 C ABI。** 关键入口的寄存器取参方式符合 Delphi register ABI。`LinkIOInit` 使用 EAX/EDX，`LinkIOINITEx` 使用 EAX/EDX/ECX；缓冲区函数也存在寄存器取参。仅用 `CDLL`/`WinDLL` 声明函数名不构成正确调用。当前恢复的是局部调用方式，不是完整、经厂家确认的头文件。
3. **HAL 自身有较多运行逻辑。** 它含窗口操作、工作线程、同步对象与管道相关代码，另有疑似消息泵调用路径。去掉 Term 仍然会保留这些模块，不能假定它是一层无状态的 USB 转发函数。
4. **初始化不是只读操作。** 初始化链进入 FT_Open、超时/USB参数设置及 FT_Purge；会清除通信队列。它还建立两个设备通道和后台工作逻辑。不能把 `LinkIOInit()` 当成无副作用的“设备信息查询”。

### 关键证据

初始化跟踪经过 `0x40045EA4 -> 0x40044E14 -> 0x40044920 -> 0x400447E0 -> 0x40041F70`。双通道打开调用点为 `0x40044897`、`0x400448A8`；D2XX 调用点见下一节。

`LinkIODone` 从 `0x40046304` 开始；其结束路径存在循环、消息处理调用和 100 ms Sleep，不能仅凭方法名假定关闭必定立即完成。

更精确地说，该循环中的 `0x4002A390` 是疑似应用消息处理函数，尚无符号名确认；局部循环本身没有可见截止计数。线程创建调用点包括 `0x400442B6`、`0x400442D2`、`0x40044371`、`0x4004438D`、`0x400443ED`；命名管道调用点为 `0x400459E1`；窗口操作包括 `0x40044AB5` 的 SetParent、`0x40044B21` 的 SetWindowPos。这些说明内部机制复杂，不构成用户当前卡死的根因证明。

`ParSendBuffer` / `ParGetBuffer` 的局部正常路径还显示：DL 长度为 0 时按 256 字节处理，返回 AL 为字节累加值，不能误当传输字节数；这也不能证明仪器线上测量帧使用同一校验方式。

另一个限制是 `USB2HAL.dll` 带 UPX 节布局，不能对其压缩入口直接套用 FTDIHAL 的反汇编结论。本次没有执行或动态解包；`USB2HAL_ini.dll` 也不能只因名字相近就当成等价替代物。

### 对项目的影响

纯粹为了复用 x86 HAL 引入一个长期运行的 32 位设备代理，会重新增加进程边界，也不符合当前仓库禁止新增设备服务/旧 worker IPC 的约束。本次不创建这种服务。

可在仓库外做独立 x86 ABI 研究程序，但它只能是研究工具。将来若要作为产品运行时，必须先明确架构变更，而不是偷偷作为回退路径加入。

## 3. 路径二：直接使用 FTD2XX

目标结构：`ZahnerFlow -> 自己的双通道协议实现 -> x64 FTD2XX -> USB`。

### 已恢复的传输层行为

| 行为 | 静态调用点 / 参数 |
|---|---|
| 打开已选设备索引 | `0x40041F84`，FT_Open |
| 读写超时设置 | `0x40041FA4`，100 ms / 100 ms |
| USB 传输尺寸设置 | `0x40041FB9`，`0x3000` / `0x3000`（12,288 字节） |
| 延迟计时器 | `0x40041FC6`，2 ms |
| 清队列 | `0x4004212D`，常规初始化路径组合 RX 与 TX 标志 |

这些值是该版本 HAL 的实际参数，不是新驱动已经验证的最佳参数，也不是 Remote2/EIS 完成超时。`USB2BUF=8192` 是另一层配置，不能与 D2XX 的 `0x3000` 混为一项。

`0x40042438` 附近的枚举逻辑检查设备描述和序列号；可以看到 Zahner、IM6、Zennium、Thalesbox 及多个 Zennium 型号字符串，以及追加 `A`/`B` 后缀后分别匹配通道。两个枚举索引分别传给 FT_Open。因此不能通过 `FT_Open(0)` 默认认定找到正确仪器，也不能只处理一个通道。

另一控制路径在 `0x40041EAC`、`0x40041EFF` 调用 FT_SetBitMode，模式参数为 `0x20`，掩码由参数计算后再回到 `0xF0`。它不应被抄作普通数据初始化配置；其控制作用须结合上层调用和硬件验证后才可采用。

### 能省掉什么、还缺什么

使用匹配位数的 D2XX API，有机会省去 x86 HAL 的特殊 ABI、内部线程/窗口和旧进程依赖。[FTDI 官方提供 x86/x64 D2XX](https://ftdichip.com/drivers/d2xx-drivers/)。但必须自行实现设备识别、两个通道的数据收发、缓冲和时序，以及下节的工作站主机协议。API 语义以 [D2XX 编程指南](https://ftdichip.com/wp-content/uploads/2023/09/D2XX_Programmers_Guide.pdf) 为参照，不能把该指南当成 Zennium 协议文档。

目前尚未确认所有 USB 帧边界、应答、校验、复位后握手和测量命令传输方式；更未证明向 FT_Write 写入 `1:CURRENT:` 就能得到电流值。公开 Remote2 ASCII 是上层接口，不是已确认的裸 USB 协议。

## 4. 两条路径共同需要替代的 Term 服务

安装包 `remote2.is_` 比“Term 可能提供文件服务”给出了更具体的证据：

- `sc_dev$=CHR$(27)+CHR$(126)`，即终端控制前缀 `1B 7E`。
- `sc_check` 在终端设备 `3` 上输出此前缀、`00 01`、连接名和 NUL，再通过 INPUT 等待主机回答连接编号。
- `comread` 输出前缀、连接编号与 `07`，再 INPUT 等待客户端命令。
- `comwrite` 输出前缀、连接编号、`08`、结果字符串、CR 与 NUL。
- `dosaveeis` 调用 `meas_save_eis(65,...)`，并继续通过设备 `65` 打开结果、导出 ASCII。

ANDIBasic 手册将 Dev3 定义为终端，Dev65 定义为 PC 文件系统。也就是说，仪器端 Remote2 会向电脑请求服务，并非只被动接收一个测量命令。

这些字节是脚本构造的**终端层消息**，不是已经确认可原样写入 FT_Write 的 USB 帧。协议研究必须继续贯通终端消息与 HAL 双通道传输之间的映射。

可以考虑保留仪器上已有的 Thales/Remote2，只实现必要的主机服务；若改写仪器端脚本以减少图形和文件依赖，则会引入新的设备端程序范围，同样需要验证加载、执行和恢复。两种办法目前都只是候选方案。

安装手册还明确说明校准数据与设备对应。即使仅保留少量测量能力，也不能绕过或替换未知的设备专属校准数据；本次没有还原其加载和使用全过程。

## 5. 最小可行性验证应如何分级

1. **确认硬件路径。** 在实验电脑上读取实际型号、USB 硬件 ID、A/B 通道描述及序列号、运行配置。安装包默认选择 FTDI 不代表这台仪器一定如此。
2. **先做离线协议验证。** 补齐调用关系、消息格式，利用记录的通信数据验证解码、分包和双通道关联，不先写控制命令。
3. **把设备枚举与初始化分开。** D2XX 枚举只能验证电脑看见接口，不等于读取工作站状态；HAL 初始化会配置和清队列，必须作为单独的受控实验。
4. **验证 Term 缺席时的主机服务闭环。** 明确工作站冷启动和已运行状态下所需服务，建立连接后能够正确处理请求并退出，不能仅仅成功 FT_Open。
5. **再验证一个只读测量。** 输出关闭条件下读取一个电位值，并与厂商程序的可比读数核对；然后才逐步进入输出控制和 EIS。不能把 HAL GetVersion 或 USB 描述字符串当成已读到仪器测量状态。

在获得第 4、5 步证据前，不把任何一条路径接入生产工作流。已知电化学控制必须继续留在验证过的接口边界内。

## 6. 验证与版本

本次完成静态研究及关键地址复核，未进行真机直连。研究没有更改应用架构、接口或设备行为，版本 `2.2.1 -> 2.2.1`，不升级。
